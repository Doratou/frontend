# زیرساخت مشترک API

این پوشه مسئول ارتباط HTTP مشترک بین تمام قابلیت‌هاست:

- `client.ts`: ساخت Axios instance، آدرس پایه از env، timeout، تنظیم credentials و interceptor مشترک.
- `env.ts`: خواندن و اعتبارسنجی متغیرهای عمومی مربوط به API.
- `error.ts`: مدل `ApiError`، تبدیل خطاهای شبکه/HTTP و `getApiErrorMessage` برای پیام امن با نگاشت status اختصاصی هر عملیات. نگاشت‌های مخصوص یک قابلیت کنار همان قابلیت قرار می‌گیرند.

درخواست‌های محصول مثل ورود، دریافت اکیپ و ثبت هزینه در این پوشه قرار نمی‌گیرند؛ محل آن‌ها `features/<feature>/api` است. تمام آن درخواست‌ها باید `apiClient` را از `@/lib/api/client` مصرف کنند.

تنظیمات cache و retry مربوط به TanStack Query در `../query-client.ts` است. `AuthSession` در قابلیت auth، interceptor مربوط به Bearer و refresh توکن را روی همین client نصب می‌کند؛ زیرساخت عمومی به قابلیت auth وابسته نیست.

## قرارداد ساختار API قابلیت‌ها

این قرارداد برای Auth، اکیپ‌ها و قابلیت‌های بعدی مشترک است. هدف، ثابت‌بودن مسئولیت‌هاست؛ برای هر endpoint نیازی به ساختن چند فایل یا یک کلاس سرویس نیست.

| مسئولیت                                          | محل                                                                 |
| ------------------------------------------------ | ------------------------------------------------------------------- |
| base URL، timeout، credentials و خطای عمومی HTTP | همین پوشه                                                           |
| مسیر، ورودی درخواست و تبدیل پاسخ هر عملیات       | `features/<feature>/api`                                            |
| schema پاسخ سرور و تبدیل DTO به مدل داخلی        | `contracts.ts` همان API یا کنار عملیات، اگر فقط همان‌جا مصرف می‌شود |
| کلیدهای کش و mutation                            | `query-keys.ts` همان قابلیت                                         |
| query، mutation و invalidation مرتبط             | کنار عملیات در API؛ hookهای وابسته به UI در `hooks` همان قابلیت     |
| نمایش خطا، اتصال خطا به فرم و navigation         | `components` یا `hooks` همان قابلیت                                 |

### درخواست و پاسخ

- تمام درخواست‌های بک‌اند از `apiClient` مشترک استفاده می‌کنند؛ Axios instance یا wrapperهای عمومی `getData` و `postData` برای هر قابلیت نسازید.
- نام عملیات معنای محصول را بیان می‌کند؛ مثل `getGroups` یا `createGroup`. عملیات کوچک و مرتبط می‌توانند در یک فایل باشند؛ با بزرگ‌شدن قابلیت، فایل‌هایی مثل `get-groups.ts` بسازید. `auth-api.ts` فعلاً مجموعهٔ عملیات مرتبط Auth است.
- ورودی‌های مرتبط را در یک object بگیرید؛ شناسهٔ تکی می‌تواند پارامتر مستقیم باشد. `signal?: AbortSignal` پارامتر آخر است و به Axios منتقل می‌شود. در query، همان `signal` دریافتی از `queryFn` را استفاده کنید.
- پاسخ HTTP را `unknown` بگیرید و در مرز API با Zod اعتبارسنجی کنید. generic مثل `apiClient.get<Group>()` به‌تنهایی اعتبارسنجی زمان اجرا نیست. اگر schema موجود است، نوع DTO را با `z.infer` از آن بگیرید.
- تابع API دادهٔ معتبر و موردنیاز مصرف‌کننده را برمی‌گرداند، نه `AxiosResponse`. تبدیل نام فیلدها یا تاریخ‌ها به مدل داخلی همین‌جا انجام می‌شود. عملیات بدون دادهٔ مصرفی `Promise<void>` برمی‌گردانند.
- شکل envelope از قرارداد واقعی بک‌اند می‌آید. فعلاً Auth پاسخ `{success: true, data: ...}` دارد؛ این شکل را بدون قرارداد به endpointهای بعدی تعمیم ندهید. پاسخ `204` نیز فقط برای عملیاتی مجاز است که قراردادش پاسخ بدون بدنه دارد.

نمونهٔ موجود در Auth، داخل تابع محلی `post`:

```ts
const response = await apiClient.post<unknown>(path, input, {
  signal,
  headers: captcha
    ? { 'X-Captcha-ID': captcha.id, 'X-Captcha-Code': captcha.code }
    : undefined,
});
const envelope = authEnvelopeSchema.parse(response.data);
return schema.parse(envelope.data);
```

در این نمونه، schemaهای envelope و داده در `features/auth/api/contracts.ts` تعریف می‌شوند. helper مربوط به POST در همان Auth می‌ماند؛ تا زمانی که قابلیت دیگری همین رفتار را واقعاً نیاز ندارد، helper مشترک جدیدی لازم نیست.

### خطا و رابط کاربری

- خطای HTTP/شبکه در کلاینت مشترک به `ApiError` تبدیل می‌شود. قواعد اختصاصی یک قابلیت، مثل OTP منقضی‌شده، در API همان قابلیت به خطای اختصاصی تبدیل می‌شوند؛ متن خام سرور نمایش داده نمی‌شود.
- `catch` فقط وقتی لازم است که خطا را به خطای اختصاصی تبدیل کنید یا cleanup لازم انجام دهید. `console.error` و سپس `throw` در تمام عملیات تکرار نمی‌شود.
- لغو درخواست، خطای قابل نمایش به کاربر نیست. خطای cancellation را حفظ کنید تا hook یا کامپوننت بتواند آن را نادیده بگیرد.
- schema نامعتبر نیز باید عملیات را ناموفق کند؛ به‌جای دادهٔ خراب، دادهٔ پیش‌فرض موفق برنگردانید. در Auth این خطا به پیام کنترل‌شدهٔ همان قابلیت تبدیل می‌شود.
- API مسئول Toast، `navigate` یا `form.setError` نیست. نمونه‌های Auth: `hooks/use-auth-mutation.ts` مسئول پیام عمومی، `components/auth-form-errors.ts` مسئول اتصال فیلدهای مجاز و `hooks/use-complete-sign-in.ts` مسئول انتقال پس از ورود است.
- مدیریت توکن، refresh و ثبت/پاک‌کردن نشست بخشی از پروتکل Auth است و در adapter آن باقی می‌ماند؛ رفتار صفحه به آن اضافه نمی‌شود.

### Query و mutation

- هر قابلیت ریشهٔ کلید خودش را دارد؛ مثل `['groups']`. query و invalidation از یک `query-keys.ts` مشترک استفاده می‌کنند. شناسه، صفحه و فیلترهای مؤثر بر پاسخ باید در کلید باشند؛ رمز، OTP و توکن نباید در کلید قرار بگیرند.
- query وابسته به شناسه یا ورودی آماده‌نشده، تا زمان آماده‌شدن با `enabled` غیرفعال می‌ماند. از `queryOptions` وقتی استفاده کنید که تعریف query بین hook، prefetch یا loader مشترک است.
- invalidation کنار mutation همان قابلیت تعریف می‌شود و فقط کلیدهای مرتبط را هدف می‌گیرد؛ کامپوننت صرفاً برای پاک‌کردن کش QueryClient جدید نمی‌سازد و از `useQueryClient()` استفاده می‌کند.
- دادهٔ سرور در Query نگهداری می‌شود و برای کپی پاسخ API، Zustand store دیگری ساخته نمی‌شود. نشست Auth استثنای فعلی است: فقط در `auth-store.ts` نگهداری می‌شود و کپی Query ندارد.
- سیاست retry عمومی در `lib/query-client.ts` است؛ mutationها خودکار تکرار نمی‌شوند. تغییر این سیاست برای عملیات مالی نیازمند قرارداد جلوگیری از تکرار در بک‌اند است.
- hookهای دارای Toast، فرم یا چرخهٔ نمایش، مثل `useAuthMutation`، در `hooks` می‌مانند. hook مربوط به Query که فقط درخواست و کش را مدیریت می‌کند می‌تواند کنار عملیات API باشد.

### مرز وابستگی‌ها

جهت وابستگی از UI به API قابلیت و سپس کلاینت مشترک است. API قابلیت نباید از پوشه‌های `components` و `hooks` رابط کاربری import کند. ESLint این مرز محلی و همچنین import مستقیم Router، React Hook Form، Sonner و Motion در فایل‌های API را بررسی می‌کند.

برای افزودن عملیات بعدی، ابتدا قرارداد واقعی endpoint را مشخص کنید؛ سپس درخواست، schema مصرفی، کلید Query در صورت نیاز و invalidation همان عملیات را اضافه کنید. پوشهٔ اکیپ‌ها تا زمان مشخص‌شدن این قرارداد endpoint ساختگی ندارد.
